# rpi-image-gen notes

Working notes on how [raspberrypi/rpi-image-gen](https://github.com/raspberrypi/rpi-image-gen) actually behaves, gathered from its own docs/source and from [jonnymacs/rpi-tutorials](https://github.com/jonnymacs/rpi-tutorials)'s example repos. None of this is derivable just from reading this repo's customization tree — it comes from the upstream framework's internals. Written down so we don't have to re-derive it.

**Everything below this point describes the pre-v1.0 pinned commit this project used through `main`.** The `adopt_2.8.0` branch migrated to the current v2.8.0 release, which is a complete architectural rewrite (new Python-driven CLI, YAML-only config, no more `profile/` files, `.cfg`/`.options` fully removed) — see the "v2.8.0 migration" section at the end of this file for what changed and what's still true.

## The hook lifecycle — and the bug it caused us

rpi-image-gen builds in phases (`docs/execution/index.adoc` in the upstream repo):

| Phase | Context | Classification | When |
|---|---|---|---|
| setup | bdebstrap | bundle | after output dir creation, before packages installed |
| pre-build | bdebstrap | single | within setup |
| extract | bdebstrap | bundle | after `Essential:yes` packages extracted |
| essential | bdebstrap | bundle | after essential packages installed |
| **customize** | **bdebstrap** | bundle | **after all packages installed, before cleanup** |
| cleanup | bdebstrap | bundle | after customize |
| **post-build** | **main** | single | **after bdebstrap has already exited** |
| sbom / pre-image / post-image / finalize / deploy | main | single | later stages |

The critical column is **Context**. Everything through `cleanup` runs *inside* the `mmdebstrap`/`bdebstrap` process, which owns a private mount namespace with `/proc`, `sysfs`, `devpts` mounted into the rootfs. `post-build` explicitly runs in the `main` context, after that process has exited and torn its own mounts down.

**This means `device/<class>/post-build.sh` and `image/<layout>/post-build.sh` are structurally the wrong place for anything needing a working chroot** (`apt-get`, `pip install`, anything that touches `/dev/null`, DNS, etc.). We hit this directly: `chroot $rootfs apt-get update` inside `device/pi5/post-build.sh` failed with `apt-key: cannot create /dev/null: Permission denied` — there's no `/dev` in the rootfs at that point. Manually bind-mounting `/dev`/`/proc`/`/sys` ourselves in `post-build.sh` is fighting the framework (racing bdebstrap's own mount/unmount lifecycle) rather than using its supported extension point, and isn't reliable.

Every real-world example confirms `post-build.sh` is meant only for **plain file writes** into the rootfs — no chroot execution needed. E.g. `rpi-ble-server`'s `device/pi5/post-build.sh` just does:
```sh
cat <<EOF > $1/etc/modules
i2c-dev
i2c-bcm2835
EOF
```

## Where package/software installs actually belong

**`bdebstrap/customizeNN-*` scripts**, placed next to the image layout (or under a device asset dir), run during the `customize` phase — bundle-classified, discovered from `bdebstrap/` subdirectories in this order: device asset dir → image asset dir → `SRCROOT/bdebstrap` → built-in `IGROOT/scripts/bdebstrap`, executed in alphanumeric-basename order per phase. Because this runs *inside* the mmdebstrap-owned chroot, plain `chroot $1 apt install -y ...` and `chroot $1 <anything>` just work — no manual mounting needed.

This repo already had a working example of this pattern before we understood why it worked: `pinball/image/mbr/simple_dual/bdebstrap/customize05-pkgs` (installs `dosfstools`/`e2fsprogs`, vendored from rpi-image-gen-example). MPF installation now lives in `customize10-mpf` in the same directory, following the same pattern — **confirmed working**: `apt install` (411 packages, ~250MB) and `pip install "mpf~=0.57.0" "mpf-mc~=0.57.0"` both completed cleanly with no mount errors, resolving to `mpf==0.57.5` and `mpf-mc==0.57.1`. Total build time ~10 minutes on Docker Desktop for Mac (Apple Silicon, native arm64, no QEMU emulation).

Real examples from `rpi-tutorials` confirm this is the standard way to install anything nontrivial:
- `rpi-lamp-stack`: `chroot $1 php composer-setup.php ...`, `chroot $1 runuser -u www-data -- bash -c "composer install ..."`
- `rpi-tradingstrategy-ai-part-2`: `chroot $1 runuser -u $IGconf_device_user1 -- bash -c "pipx install poetry"` (and similarly for `pip`/`npm` — run as the non-root device user via `runuser` when the installed tool expects a normal user's `$HOME`)
- `rpi-web-kiosk`: `chroot $1 runuser -u $IGconf_device_user1 -- bash -c "npm install --prefix ..."`

We install as root and `chown` the result to `$IGconf_device_user1` afterward instead of using `runuser` throughout, since a venv doesn't care who created it — just who can write to it later.

## The declarative alternative (not used here, but exists)

For plain apt package lists (no custom logic needed), rpi-image-gen supports a declarative path that skips hook scripts entirely:
- A `packages:` list in a config/options file becomes `IGconf_packages_N` variables, consumed automatically by the built-in `scripts/bdebstrap/customize20-packages` hook.
- A custom layer YAML can declare `mmdebstrap: packages: [...]` directly (e.g. upstream's `layer/rpi/misc-utils.yaml`).
- `rpi-tutorials`' `meta/*.yaml` files use this for third-party APT repos too — e.g. `meta/php.yaml` adds the sury.org PHP PPA via `mmdebstrap.setup-hooks` before listing PHP packages.

We didn't use this because MPF needs a venv + pip install + chown, not just apt packages — a `customizeNN-*` script is the right tool once you need actual shell logic, not just a package list.

## Layers, device/image/profile — how they relate

- **Layers** are the composable unit: YAML files with `X-Env-Layer-*` metadata, either `mmdebstrap:`-native (packages/customize-hooks consumed directly by mmdebstrap) or plain shell hooks. `device/pi5/device.yaml` upstream is itself a layer (category `device`), not a hooks container.
- **`<layer>.rootfs-overlay/`** — a directory named after a layer file, sitting next to it, gets copied into the rootfs automatically during `customize`, before that layer's own hooks run. Useful for shipping static files without writing a hook script at all.
- `examples/custom_layers/` in the upstream repo is the canonical worked example of authoring your own layer + config + traits from scratch (`rpi-image-gen build -S ./examples/custom_layers/ -c acme-integration.yaml`) — worth reading if this project ever needs a real custom layer instead of a `customizeNN-*` script bolted onto the `mbr/simple_dual` layout.

## Container/mount requirements

From upstream's `README.adoc`, quoted directly:

> The build invokes `mmdebstrap` to create a chroot and mount pseudo-filesystems (proc, sysfs, devpts) inside a private mount namespace, which requires `CAP_SYS_ADMIN` or equivalent (eg, `--privileged` or `--security-opt=unconfined` depending on rootless/container setup). The build will fail without that capability. [...] For a supported path, run on native Debian Bookworm/Trixie arm64.

Docker Desktop on Mac (what we build on) isn't an officially supported path — it works because `docker-compose.yml` sets `privileged: true`, but isn't guaranteed by upstream. In practice: `/dev` and `/proc` bind-mounts succeed in our container even when a *fresh* `mount -t proc`/`mount -t sysfs` doesn't (we saw bdebstrap itself fall back from a failed plain mount to a working bind-mount for `/proc` during the base build; `/sys` never got a working fallback, but nothing we've needed so far requires it).

`jonnymacs/rpi-tutorials` is just an index README pointing at separate repos — no content of its own. Repos and what they demonstrate:

- `rpi-web-kiosk`, `rpi-with-splash-screen` — Chromium kiosk / Plymouth splash screen tutorials, both ship dual `device/pi4` and `device/pi5` trees (useful precedent for our pi5-only setup).

- `rpi-ble-server` — Rust BLE GATT server, `class=pi5` only, I2C RTC (`dtoverlay=i2c-rtc,ds3231` in `config.txt` + `i2c-dev`/`i2c-bcm2835` in `/etc/modules` via `post-build.sh`) — our closest hardware-integration precedent, though P-ROC is USB/FTDI-based so we don't need any of its I2C/dtoverlay config.

## Resolved: MPF install, confirmed working

The `customize10-mpf` hook succeeded on the first try after moving it out of `post-build.sh`. Notes for next time:
- **pip resolved `mpf-0.57.5` and `mpf-mc-0.57.1`** from the `~=0.57.0` range pins — both within the 0.57 line as intended.
- **piwheels (`https://www.piwheels.org/simple`) is used automatically** alongside PyPI inside the chroot's pip config (this comes from Raspberry Pi OS's default pip config, inherited into the rootfs) — this is why `Pillow` installed as a prebuilt arm64 wheel instantly instead of compiling from source. `psutil`, `mpf-mc`, and `ffpyplayer` still built from source (each took well under a minute), confirming the `-dev` headers we installed (GStreamer/SDL2/ffmpeg) were the right/sufficient set — no missing-header build failures.
- `mpf-mc` still depends on **Kivy 2.2.1** under the hood (despite mpf-mc having moved to GStreamer/SDL2 for actual media rendering) — Kivy itself has a prebuilt arm64 wheel on PyPI, so this added no build time.
- No `runuser`/non-root complications: installing as root inside the chroot and `chown`-ing `/opt/mpf` to `$IGconf_device_user1` afterward worked with zero issues.
- Full build time end-to-end (`./build.sh`, base rootfs + `customize10-mpf` + image packaging) was **~10 minutes** on Docker Desktop for Mac, Apple Silicon (native arm64 — no QEMU emulation tax, unlike the amd64 path mentioned in `CLAUDE.local.md`).

## `ssh_user1=y` does NOT work on the apt-min64 profile

`device/build.defaults` documents `ssh_user1` as: "If y, automatically include net-misc/openssh-server in the profile to enable SSH access." We set `ssh_user1=y` in `pinball.options` from the start, assumed it worked, and shipped a build claiming "SSH enabled" — it doesn't.

**Verified by mounting the built image directly** (no need to flash/boot a Pi to check this — much faster feedback loop):
```sh
fdisk -lu pinball-*.img   # find the ext4 (root) partition's start sector, multiply by 512 for byte offset
mount -o loop,ro,offset=<bytes> pinball-*.img /mnt/root
grep "^Package: openssh-server" /mnt/root/var/lib/dpkg/status   # nothing — not installed
ls /mnt/root/etc/ssh/                                            # doesn't exist
```
(Needs a Linux mount, so run it inside a throwaway `docker run --privileged -v <deploy-dir>:/data:ro debian:bookworm bash` — same privileged-container mechanism the build itself uses, not the host Mac directly.)

The `ssh_user1` flag is presumably consumed by some OTHER profile's layer (or a newer rpi-image-gen version) that conditionally adds `openssh-server` based on it — `apt-min64` doesn't wire it up. Fixed properly via `bdebstrap/customize08-ssh`, following the same working pattern as `customize05-pkgs`/`customize10-mpf`: `chroot $1 apt install -y openssh-server && chroot $1 systemctl enable ssh`. Left `ssh_user1=y` in `pinball.options` anyway (harmless, may matter on a different profile) but the comment there now points at the real mechanism.

**Caveat for later**: baking `openssh-server` in at image-build time means its host keys are generated once, at build time, and are then identical across every device flashed from the same `.img` — fine for a single hobby machine, but if this image is ever flashed onto multiple pinball cabinets, add a first-boot service that deletes and regenerates `/etc/ssh/ssh_host_*` keys (the standard fix Raspberry Pi OS itself uses) rather than shipping shared keys.

## WiFi: baked in via `customize09-wifi`, no NetworkManager/raspi-config here

This image uses `systemd-networkd` (from the `sys-apps/systemd-net-min` layer), not NetworkManager — `raspi-config`'s usual wifi wizard doesn't apply. Also, `apt-min64` ships neither `wpasupplicant` nor `firmware-brcm80211` (the Pi 5's Broadcom wifi chip firmware), so wifi doesn't work out of the box at all, same story as SSH above.

`customize09-wifi` installs both packages, writes `/etc/wpa_supplicant/wpa_supplicant-wlan0.conf` (SSID/PSK) and a `systemd-networkd` `.network` unit for `wlan0` (`DHCP=yes`, mirroring the existing `01-eth0.network` pattern from the `netgen eth0` built-in hook), then enables `wpa_supplicant@wlan0.service`.

**Credentials never touch git**: real SSID/PSK live in `pinball/wifi-credentials.env` (gitignored), sourced by the hook via its known absolute path inside the build container (`/home/imagegen/pinball/wifi-credentials.env` — matches `docker-compose.yml`'s bind mount + `RPI_BUILD_USER`/`RPI_CUSTOMIZATIONS_DIR` in `build.sh`). Anyone rebuilding this repo fresh needs to create that file themselves (see README).

No `country=` set in the wpa_supplicant config — wifi still works without it (falls back to the world regulatory domain), just without your country's extended channel set. Add `country=<ISO 3166-1 alpha-2>` inside the hook if you hit connectivity issues.

## `mpf` crashed on every invocation — pkg_resources bug, not our packaging

Discovered by chrooting into the built image and running the venv's `mpf` binary directly (mounting `/dev`+`/proc` first, same as the customize hooks need) — this is a much faster way to sanity-check "does the installed software actually run" than flashing/booting real hardware:
```sh
mount -o loop,offset=<root-partition-bytes> pinball-*.img /mnt/root
mount --bind /dev /mnt/root/dev; mount --bind /proc /mnt/root/proc
chroot /mnt/root /opt/mpf/venv/bin/mpf --help
```
This crashed immediately with `pkg_resources.DistributionNotFound: The 'ruamel.yaml.clib>=0.2.7' distribution was not found`, thrown from `mpf`'s own CLI loader (`mpf/commands/__init__.py`'s `get_external_commands()`, which uses the legacy `pkg_resources` API to load `mpf.command` entry points contributed by `mpf-mc`).

**Root cause, reproduced independently** on a clean `python:3.11-bookworm` container (nothing to do with our chroot/piwheels/arm64 setup — this is a real upstream bug hit by `mpf~=0.57.0` + `setuptools~=72.2.0`, the exact setuptools version `mpf` itself pins):
```sh
pip install "setuptools~=72.2.0" "ruamel.yaml==0.18.6"
python3 -c "import pkg_resources; pkg_resources.require('ruamel.yaml.clib>=0.2.7')"
# -> pkg_resources.DistributionNotFound, even though pip installed it and `pip check` is clean
```
`ruamel.yaml.clib`'s wheel installs a dist-info directory named `ruamel_yaml_clib-0.2.15.dist-info` (dots normalized to underscores, standard modern packaging practice for a project name containing literal dots). The legacy `pkg_resources.working_set` scanner in `setuptools` 72.2.0 fails to match the requirement string `ruamel.yaml.clib>=0.2.7` against that underscore-normalized directory name — a known class of `pkg_resources`/dotted-project-name bug, unrelated to piwheels, arm64, or anything in this repo.

**Verified fix**: duplicate that dist-info directory under its dotted name (`ruamel.yaml.clib-0.2.15.dist-info`) right after installing MPF — purely additive, doesn't touch any actual installed files, and confirmed (via the same clean-container repro, then against a copy of this image's actual venv) to make `pkg_resources.require(...)` resolve correctly and `mpf --help` run without error. Implemented in `customize10-mpf`.

**Confirmed on real hardware** after rebuilding and flashing: SSH, WiFi, and `mpf` (with this fix) all work on an actual Pi 5.

## Confirmed CLI usage (from reading `mpf/commands/__init__.py` and `mpf/commands/both.py` directly)

- `mpf [machine_path]` — defaults to the `game` command (core engine only, no display). `machine_path` is optional if the current directory has a `config/` subfolder (auto-detected as the machine folder).
- `mpf mc [machine_path]` — media controller only (`mpfmc.commands.mc`, contributed via mpf-mc's `mpf.command` entry point).
- `mpf both [machine_path]` — **the one to actually use for a full running machine**: spawns the media controller as a subprocess and runs the core engine in the main process, both from one command (`mpf/commands/both.py`).
- No first-boot systemd service exists yet (deliberate — see earlier "Manual for now" decision) — start manually over SSH: `cd ~/machine && mpf both`, or `mpf both ~/machine` from anywhere.
- `/opt/mpf/venv/bin` is added to `$PATH` via `/etc/profile.d/mpf-path.sh` (written by `customize10-mpf`, same mechanism the base image already uses for its own `/etc/profile.d/01local.sh`) — works for both the autologin console session and interactive SSH logins, since both are login shells that source `/etc/profile.d/*.sh`. Not yet rebuilt/verified since adding this.

## Root filesystem has zero free space by default — `apt install`/`git clone` fail with "No space left on device"

`root_part_size=100%` (the layout's default, unchanged by us) means the root partition is built to *exactly* fit its contents at build time — no headroom at all, on every image, regardless of the SD card/USB drive's actual size. This isn't a permissions/read-only issue (the filesystem genuinely does mount `rw`) — it's a real disk-full condition, reproduced ourselves earlier while debugging (`cp: cannot create directory ...: No space left on device` when trying to write into the mounted image directly).

**Fix, adapted from `jonnymacs/rpi-auto-resize-root`** (a working `rpi-tutorials` example whose entire purpose is exactly this problem) — full first-boot auto-expand, implemented in a single hook, `customize06-resize-root`:
- Delegates the partition-table resize to **`raspi-config --expand-rootfs`** (installed via `apt install raspi-config fdisk`) rather than hand-rolling `parted`/`growpart` logic. `raspi-config`'s own implementation (`RPi-Distro/raspi-config`, `do_expand_rootfs()`) does device detection fully dynamically via `findmnt / -o source -n` + `lsblk -no pkname` — no hardcoded `/dev/mmcblk0p2`/`/dev/sda2` assumptions, so it works whether the image ends up on an SD card, USB drive, or NVMe.
- Two-stage because a mounted partition can't be resized live: `fdisk` deletes+recreates the root partition at its original start sector with no explicit end (fills the disk) on **boot 1**, then **immediately hard-reboots via `echo b > /proc/sysrq-trigger`** (not `systemctl reboot`) so the kernel re-reads the new partition table right away instead of waiting for a manual reboot. On **boot 2** onward, our own trigger script runs `resize2fs` directly on the root device — a safe no-op once the filesystem already fills the partition, so it's fine to leave the systemd service enabled forever rather than disabling it after success.
- **This means first boot after flashing reboots itself once automatically** — expected behavior, not a crash, if you're watching the console/SSH connection drop and come back.
- `dosfstools`/`e2fsprogs` (needed for `resize2fs`) were already installed via `customize05-pkgs`, inherited unchanged from macmind — only `raspi-config`/`fdisk` needed adding. `fdisk` isn't guaranteed present on a minimal profile (Debian split it out of `util-linux-core` into its own package), hence installing it explicitly rather than assuming it's already there.

**Confirmed on real hardware, with a real bug found and fixed along the way.** The partition-table resize worked correctly (`fdisk -l` after the fact showed the root partition correctly grown from 1.7G to 14.5G) — but the original design (mirroring `jonnymacs/rpi-auto-resize-root` exactly) relied on `raspi-config`'s own self-registered `/etc/init.d/resize2fs_once` script to grow the filesystem on the second boot, and that file came out **empty (0 bytes)** on the actual device — it never ran, the automatic reboot never fired (confirmed via `journalctl -u expand-rootfs` showing the service cleanly "Finished" with no gap for a reboot), and the filesystem stayed at its original size until manually run.

Root cause not fully pinned down: reproducing the *exact* heredoc-write from `do_expand_rootfs()` in isolation (same `/bin/sh` = dash, same no-TTY stdin-from-`/dev/null` context matching a systemd service) wrote the file correctly every time — so whatever actually broke it is specific to the real invocation context (live-mounted root, run via `raspi-config --expand-rootfs`'s full call graph, possibly the trailing `whiptail --msgbox` call inside `do_expand_rootfs()` failing since `INTERACTIVE=True` is hardcoded at the top of `raspi-config` with no TTY-detection override — this is also probably *why* the reboot never fired in the original design, since `raspi-config --expand-rootfs`'s own exit code is unreliable here and our very first version had no `set -e`, so that wasn't the direct cause of the missing reboot, but it's suggestive of the same underlying "no TTY" class of problem).

**Fix**: stopped depending on `raspi-config`'s internal resize2fs_once scheduling entirely. Our own trigger script now calls `resize2fs "$(findmnt / -o source -n)"` directly once a `/boot/firstboot_resized` sentinel shows the partition step already ran — a single well-tested, well-understood command, no dependency on `raspi-config`'s internal state machine. Manually verified as the correct fix on the affected device (`sudo resize2fs /dev/mmcblk0p2` after a manual reboot grew the filesystem to 14.5G immediately) before folding it into the hook.

**Also worth noting for future edits to `expand-rootfs.sh`**: it deliberately has no `set -e`. `raspi-config`'s own comment in `do_expand_rootfs()` says fdisk's exit code will likely be non-zero on a mounted root partition, and the trailing whiptail call has no TTY to render into — both look like failures but aren't fatal ones; the script needs `touch`/`sync`/reboot to run regardless of `raspi-config`'s own exit status.

## DNS resolution is broken by default — `ping github.com` fails, `ping 8.8.8.8` works

`/etc/resolv.conf` in the built rootfs is a **leftover from the Docker build container itself**: debootstrap copies the build host's `/etc/resolv.conf` into the target rootfs so `apt` can resolve `deb.debian.org`/`archive.raspberrypi.com` *during the build* — nobody ever swaps it out for something that makes sense on the actual device. Confirmed by inspecting the built image directly (`cat /mnt/root/etc/resolv.conf`): it's a Docker-generated file pointing at `nameserver 127.0.0.11` (Docker's internal per-container DNS proxy), which obviously doesn't exist once flashed onto a Pi. Symptom is exactly "Temporary failure in name resolution" — DNS-specific, not a general connectivity problem, since the network itself (IP/routing over eth0/wlan0) works fine.

Root cause has two parts, both present in the `apt-min64` profile:
1. The stale build-time `resolv.conf` never gets replaced.
2. **`systemd-resolved` isn't installed** — and it's specifically `systemd-resolved`'s job to take the DNS servers `systemd-networkd`'s DHCP client learns and turn them into a working `/etc/resolv.conf`. `systemd-networkd` alone has no mechanism to write `/etc/resolv.conf` itself; that hand-off is by design delegated to resolved. Both `01-eth0.network` (built-in) and our own `02-wlan0.network` already have `DHCP=yes` (which implies `UseDNS=yes` by default) — they were fine all along, just with nothing downstream to consume the DNS info they were already receiving.

**Fix, `customize95-dns`**: `apt install systemd-resolved`, enable it, then force-replace `/etc/resolv.conf` with the standard `/run/systemd/resolve/stub-resolv.conf` symlink ourselves (rather than trust `systemd-resolved`'s postinst to handle an already-present, foreign, Docker-injected file correctly).

**Critical ordering constraint — this hook MUST run last** (hence the `95` prefix, highest of all our `customizeNN-*` hooks). The symlink it creates only resolves to a real file once `systemd-resolved` is actually *running*, which it isn't during the build (a chroot has no init system). Any `apt install` inside the chroot *after* this hook runs would itself fail to resolve `deb.debian.org` and break the build — this would have been a nasty one to debug blind, since it only would have surfaced as a mysterious apt failure in whichever hook happened to run after it, with no obvious connection to DNS.

## v2.8.0 migration (`adopt_2.8.0` branch)

Migrated from the pre-v1.0 commit above to the current `v2.8.0` tag. This is a **complete rewrite**, not a version bump — confirmed by fetching every release's notes (v1.0.0 through v2.8.0) and diffing the actual repo tree between our old pinned commit and v2.8.0. The rewrite landed between `v1.0.0` and `v2.0.0-rc.1` (days apart); everything from v2.1 onward is incremental refinement on the new architecture.

### What changed structurally
- CLI: `./build.sh -D <dir> -c <config>.cfg -o <options>.options` → `./rpi-image-gen build -S <srcroot> -c <config>.yaml`.
- Config format: `.cfg`+`.options` (INI) → a single YAML file. INI support is fully gone as of v2.8.0 — this was a schema rewrite, not a find/replace.
- "Profiles" removed entirely. `apt-min64` no longer exists by that name — its functional equivalent is the `bookworm-minbase` layer (`layer/suite/debian/bookworm-minbase.yaml`), referenced directly by name in the config's `layer:` section.
- `image/mbr/simple_dual/` keeps its path and its `bdebstrap/customizeNN-*` hook convention (still discovered the same way), but `config.options` → `image.yaml`.
- Custom logic now belongs in **custom layer YAML files** (`pinball/layer/*.yaml`, discovered via `-S`), not a wholesale copy of the built-in image directory. `mmdebstrap: customize-hooks:` is an inline list of shell snippets right in the layer file — no separate hook script files needed. See `examples/custom_layers/` in the upstream repo for the reference pattern this project's `pinball-mpf`/`pinball-resize-root` layers are based on.
- **Layer labels become shell variable names** (`IGconf_layer_<label>`) — hyphens in a label (e.g. `wifi-reg:`) produce an invalid variable name and fail immediately. Use underscores (`wifi_reg:`).

### What got simpler (old custom hooks → new mechanism)
- `customize08-ssh` → **gone entirely**. `bookworm-minbase` requires `openssh-server` unconditionally — SSH is just always there. The `openssh-server` layer also now generates host SSH keys at boot (not build) time, fixing the "shared host keys across clones" risk we'd flagged as a known caveat under the old system.
- `customize09-wifi` (hand-rolled `wpa_supplicant`+`systemd-networkd` config) → the built-in `iwd` layer + an `iwd.network(5)` profile file (`pinball/wifi/<SSID>.psk`, gitignored, containing `[Security]\nPassphrase=...`), referenced via `iwd.profile` in the config. WiFi firmware (`firmware-brcm80211`) and `wlan0`'s DHCP config are *also* now automatic, provided by `rpi-device-base` — nothing to configure at all beyond the profile file.

### Real bug hit during migration: 16K page size breaks ext4 image generation on Pi 5

`rpi5`'s device layer requires the `rpi-linux-2712` kernel, which has a 16K page size (`IGconf_linux_page_size=16384`). `image-rpios` has a trigger that sets the ext4 mkfs block size to match the kernel's page size — but the installed `e2fsprogs` (1.47.0) can't actually create an ext4 filesystem with 16384-byte blocks:
```
Warning: 16384-byte blocks too big for system (max 4096), forced to continue
mke2fs: Could not allocate block in ext2 filesystem while populating file system
```
This happens at the very end of the build, in `generate_images` — after the entire rootfs (including all custom layers) has already built successfully, so it's an expensive failure to hit blind. Upstream's own v2.3.0 release notes actually flag this exact scenario in a migration note: *"On 16K page kernels, add `IGconf_fs_ext4_mkfs_args: -b 4096` for identical partition sizing."* Fixed in `pinball.yaml`:
```yaml
fs:
  ext4_mkfs_args: "-F -b 4096"
```

### Real hardware boot failure: `rpi-bootdev-tag` dies on partition=0, root filesystem never found

First real hardware boot attempt failed early, before Linux even fully starts:
```
ERROR: /dev/mmcblk0p0 is invalid for boot mode 1 (mmcblk0)
...
Give up waiting for root file system device
...
Dropping to a shell
```
This is a subsystem that **didn't exist in the pre-v1.0 pinned commit** — `rpi-storage-binder` (a new v2.x device layer, transitively required by every device class now) ships `bin/rpi-bootdev-tag`, a udev-IMPORT script baked into the initramfs that tags which block device the system booted from. It reads the boot partition index straight from the device tree (`/proc/device-tree/chosen/bootloader/partition`) and builds `/dev/<bootdev><sep><partition>` from it.

The script has a "legacy compat" fallback for exactly this scenario — bootloader reports partition `0` (which isn't a valid partition number), so fall back to `1` — but it's written to **explicitly skip Pi 4 and Pi 5**:
```sh
case $GEN in
   4|5);;
   *) [ $BOOT_PARTN -eq 0 ] && BOOT_PARTN=1;; # legacy compat
esac
BOOT_BLKDEV="/dev/${BOOT_DEV}${PART_SEP}${BOOT_PARTN}"
test -b "$BOOT_BLKDEV" || die "$BOOT_BLKDEV is invalid for boot mode $BOOT_MODE ($BOOT_DEV)"
```
On our real hardware, the Pi 5's bootloader reported `partition=0` anyway — exactly the case this fallback exists for, just on a generation the code assumes doesn't need it. The resulting `die()` happens inside a udev rule during early boot, so it doesn't just fail silently — it breaks boot-device tagging entirely, which cascades into the initramfs never finding a root filesystem to mount at all.

**Fix, `pinball-bootdev-fix.yaml`**: patch the installed script in place (`sed -i '/4|5);;/d' /usr/bin/rpi-bootdev-tag`) to apply the same `0`→`1` fallback unconditionally. Safe specifically for our layout since `image-rpios`'s `mbr/simple_dual` layout always has BOOT as partition 1 — this isn't a generic fix for arbitrary partition layouts, just correct for what we actually use. The layer verifies the sed actually matched something and fails the build loudly if not (in case a future rpi-image-gen version changes this file and silently no-ops the patch).

**Ordering note**: this must run after `rpi-storage-binder` installs the original file but before `customize60-initramfs-tools` bakes it into the initramfs. No special handling was needed for this — layer-YAML `customize-hooks:` (ours included) all run before the numbered `bdebstrap/customizeNN-*` files as part of the same build phase, confirmed by the build log's ordering.

**Partially fixed, second real-hardware bug found underneath.** With `pinball-bootdev-fix` applied, the specific `/dev/mmcblk0p0 is invalid` crash was confirmed gone (verified: `cat /usr/bin/rpi-bootdev-tag` inside the initramfs recovery shell showed the `4|5);;` line correctly removed — the patch reaches the initramfs copy of the script, confirming the layer-hook-before-numbered-bdebstrap-hooks ordering assumption above holds). But boot still failed the same way (`/scripts/local-block` → "Give up waiting for root file system device" → dropped to initramfs shell).

**Root cause #2, found via live diagnostics in the initramfs recovery shell** (device wasn't networked, so this was done by manually relaying commands/output):
- `/usr/bin/rpi-bootdev-tag -u -d /dev/mmcblk0p2` run by hand: succeeds (`RPI_ONBOOTDEV=1`, exit 0) — the tagging logic itself is fully fixed.
- `/dev/mmcblk0`, `/dev/mmcblk0p1`, `/dev/mmcblk0p2` device nodes all present — kernel partition enumeration is fine.
- `/dev/disk/by-slot/` exists but contains **only** `boot -> ../../mmcblk0p1` — no `system` symlink for root. That symlink is created by a second udev rule (`99-rpi-05-image.rules`, image-rpios's own) matching `ENV{RPI_ONBOOTDEV}=="1"` **and** `ENV{ID_FS_LABEL}=="ROOT"`. `root=` on the kernel cmdline is `/dev/disk/by-slot/system` (image-rpios always uses this scheme now, not a UUID) — so without that symlink, boot can never find root.
- `blkid /dev/mmcblk0p1` correctly showed `LABEL="BOOT" TYPE="vfat" ...`. `blkid /dev/mmcblk0p2` showed **only** `PARTUUID=...` — no `LABEL`, no `TYPE`, nothing else. BusyBox's minimal `blkid` (this initramfs has no `grep`, confirming it's a stripped-down environment) couldn't identify the ext4 filesystem *at all*, despite that exact filesystem mounting and reading fine everywhere else (we'd already mounted this same image ourselves multiple times via loop-mount for chroot inspection).
- Checked `image/mbr/simple_dual/mke2fs.conf`: the `ext4` fs_type defaults enable `metadata_csum,64bit` (`features = has_journal,extent,huge_file,flex_bg,metadata_csum,64bit,dir_nlink,extra_isize`). Both are known culprits for exactly this kind of minimal-blkid-probe failure — the kernel's own ext4 driver handles them fine, but simplified userspace probers (common in constrained initramfs/bootloader environments) often can't parse the newer on-disk format changes these features introduce, so `ID_FS_TYPE`/`ID_FS_LABEL` never get populated in udev's database, and any rule depending on either (like `99-rpi-05-image.rules`) silently never matches.

**Fix**: extended the same `fs.ext4_mkfs_args` override to also disable both features: `-O ^64bit,^metadata_csum`. Confirmed via `genimage.cfg.in.ext4`'s template that `<MKE2FS_EXTRAARGS>` (our override) is a clean, separate append point from genimage's own hardcoded flags (which already disable `large_file`/`huge_file` the same way, for what's presumably a similar compatibility reason) — multiple `-O` flags on one `mke2fs` invocation compose additively, no conflict.

**Build succeeded and directly verified.** The `mke2fs` invocation confirmed both fixes composed correctly with genimage's own hardcoded flags: `-O '^large_file' -O '^huge_file' ... -F -b 4096 -O ^64bit,^metadata_csum -L 'ROOT'`. Verified via `losetup -fP` + `dumpe2fs -h` directly against the built image (not just trusting the command line): actual `Filesystem features:` line confirms `64bit`/`metadata_csum` are absent (`has_journal ext_attr resize_inode dir_index filetype extent flex_bg sparse_super large_file dir_nlink extra_isize`). Also re-ran the full standard checklist (SSH, WiFi, DNS, resize-root, `pinball-bootdev-fix` applied in the rootfs copy too, dev tools, timezone, `mpf --help`) against this fresh build — all pass. **Still pending real-hardware flash/boot confirmation** — this is the actual test that matters given both bugs in this saga were only ever visible on real hardware, never via chroot inspection.

**Aside on tooling**: `losetup -fP` (partition-scanning loop devices) was unreliable in this Docker Desktop environment — worked once, then consistently failed to create the `pN` partition sub-devices on later attempts, and orphaned loop devices leaked across separate `docker run` invocations (loop devices are a host-kernel-wide resource, not container-scoped — `losetup -D` needed between attempts to clean up). The `mount -o loop,offset=<bytes>` approach (partition byte offset from `fdisk -lu`, used everywhere else in this doc) remains the reliable method; reserve `losetup -fP` only for cases specifically needing a partition-numbered block device (like `dumpe2fs`/`blkid` against a specific partition), and expect to retry/clean up.

**The `metadata_csum`/`64bit` theory was WRONG.** Real hardware re-test with that fix applied: identical failure. `blkid /dev/mmcblk0p2` at the initramfs recovery shell still showed **only** `PARTUUID=...`, nothing else — disabling those two ext4 features made no difference at all. Whatever's actually broken in this initramfs's BusyBox `blkid`, it can't identify an ext4 filesystem's type/label under any feature combination we tried. (The `-O ^64bit,^metadata_csum` override was left in place regardless — harmless, and matches genimage's own compatibility pattern for `large_file`/`huge_file` — but it is not what fixes boot.)

**Root cause #2, actually fixed: bypass blkid/udev entirely for root discovery.** Since the whole `/dev/disk/by-slot/system` mechanism depends on a successful blkid probe that this initramfs's BusyBox will never produce for ext4 (root cause unknown — possibly a build/version limitation of this specific BusyBox, not investigated further since a full bypass was simpler than chasing it), the fix doesn't try to make blkid work. Instead it uses the kernel's own native `PARTUUID=` resolution, which reads the partition table directly at boot with no blkid, no udev, and no `/dev/disk/by-slot/` involved at all:

- `pinball.yaml` pins `image.disksig` to a fixed, known value (`"0x50494e42"`) instead of leaving it as upstream's default `random`. MBR PARTUUIDs are derived from this disk signature — pinning it makes the resulting PARTUUID predictable at config time, before the image is ever built.
- A new `pinball/pre-image.sh` — a plain executable script, **not a layer** — patches `image-rpios`'s own `image/mbr/simple_dual/setup.sh` in place via `sed`, replacing every `/dev/disk/by-slot/system` reference with `PARTUUID=<disksig>-02` (partition 2, root, by standard MBR PARTUUID convention: `<8-hex-disksig>-<2-hex-partnum>`).
- This works because of an undocumented-but-real rpi-image-gen mechanism: a plain `pre-image.sh` dropped at the root of the `-S` srcroot (`pinball/pre-image.sh`) is picked up automatically by `bin/runner`'s `pre-image` hook phase — no layer registration, no metadata header needed. Confirmed by reading `bin/runner` directly: the `pre-image` phase runs, in fixed order, `IGROOT`'s own `pre-image.sh`, then `IGdevice`'s, then `IGimage`'s (`image/mbr/simple_dual/pre-image.sh` — the one that generates `genimage.cfg` and does `readlink -ef setup.sh` to bake in an absolute path), then `DEVICE_ASSET`'s, `IMAGE_ASSET`'s, and finally **`SRCROOT`'s** — ours runs last, after `image-rpios` has already pointed `genimage.cfg` at `setup.sh`'s path but well before `genimage` itself actually executes that file (which only happens later, during the `generate_images` step). Patching the file's *contents* in place at this point is safe — `genimage.cfg` only stored the path, not a snapshot.
- BOOT's by-slot symlink is left alone (`/dev/disk/by-slot/boot` in `/etc/fstab`) since vfat blkid detection already works correctly in this same initramfs — this bypass is scoped to root/ext4 only, where the actual failure is.

**Build succeeded and directly verified (2026-08-31/09-01)**: `fdisk -lu` on the built image confirms the MBR disk identifier is `0x50494e42` as configured. Mounted both partitions via explicit `losetup -o <offset>` (the `overlapping loop device` error from plain `mount -o loop,offset=...` twice against the same backing file forced using distinct loop devices instead) and confirmed directly: `/boot/firmware/cmdline.txt` contains `root=PARTUUID=50494e42-02`, and root's `/etc/fstab` contains `PARTUUID=50494e42-02  /  ext4 ...` — exactly the expected patched values, not the original `/dev/disk/by-slot/system`.

**CONFIRMED on real Pi 5 hardware (2026-09-01): boots successfully.** This closes out the entire root-discovery saga (bootdev-tag partition=0 bug → metadata_csum/64bit theory, disproven → PARTUUID bypass). The `image.disksig` + `pinball/pre-image.sh` approach is the final, working fix — no further changes needed here.

**Build-environment note**: mid-session, a leftover `docker compose up -d` container (started manually for source-diffing `rpi-image-gen`) coexisted with the one `build.sh` creates via `docker compose run --name ... -d`. `docker compose exec` (used by `build.sh`'s actual build step, with no `--name`) attached to the pre-existing container rather than the one `build.sh`'s own `$CID` variable tracked for the final `docker cp` — so the build itself succeeded inside the *other* container, and `docker cp` failed at the very end with `Could not find the file ... in container <CID>` even though the build had exited 0. Not a bug in `build.sh` under normal single-invocation use; only surfaces if a stray container for the same compose service is already running. Recovered by manually `docker cp`-ing from the container that actually had the file. Lesson: don't leave a manual `docker compose up -d` running across a `./build.sh` invocation.

## Boot splash / quiet boot

Goal: show a fullscreen custom image from power-on and hide all console text (kernel, systemd, login prompt) until the user SSHes in or `mpf-mc` takes over the display.

**`rpi-splash-screen` is a first-class built-in v2.8.0 layer — used it directly rather than hand-rolling Plymouth.** Found by grepping the upstream tree for `cmdline` references (`layer/rpi/device/splash-screen/splash-screen.yaml`). It uses the kernel's own `fullscreen_logo` feature (a Raspberry Pi kernel patch, not Plymouth) rather than a userspace splash daemon:
- Installs `rpi-splash-screen-support`, which provides `/usr/bin/configure-splash`.
- Copies the configured image to `/lib/firmware/logo.tga`, adds an `initramfs-tools` hook (`splash-screen-hook.sh`) so the logo is available as early as the initramfs, and rebuilds the initramfs.
- Edits `/boot/firmware/cmdline.txt` directly (during the bdebstrap `customize` phase, not `pre-image` — a different file/phase than our PARTUUID fix, so no ordering conflict with `pinball/pre-image.sh`): adds `fullscreen_logo=1 fullscreen_logo_name=logo.tga vt.global_cursor_default=0`, and — confirmed by inspecting the built image, not documented in the layer's own `.adoc` — also **removes `console=tty1` entirely**, leaving only `console=serial0,115200`. That's a stronger guarantee than anything we added ourselves: kernel messages can no longer target the HDMI console at all, only the serial UART.

**Image format is strict and non-obvious**: 24-bit TGA, uncompressed, ≤1920×1080, fewer than 224 colours — this isn't a Raspberry Pi Imager-style splash, it's the same class of constraint as the classic Linux console "boot logo" mechanism. `configure-splash` validates this at build time and fails loudly if violated. The layer ships `EXAMPLE-splash.sh` (ImageMagick-based) to generate a compliant placeholder, but neither the build container nor the host Mac had ImageMagick installed — instead wrote `pinball/assets/splash.tga` (a solid-background placeholder with a centered rectangle) directly in pure-Python stdlib (`struct`), hand-building the 18-byte TGA header with the image-descriptor top-left-origin bit (`0x20`) set and BGR pixel order, avoiding the bottom-up default TGA writes that'd otherwise need `-flip`. Needs replacing with real artwork before shipping — see the `splash:` block comment in `pinball.yaml` for the ImageMagick recipe.

**What `rpi-splash-screen` does NOT cover: anything after early boot finishes.** The `fullscreen_logo` mechanism is a boot-time-only kernel feature — once `multi-user.target` is reached and `getty@tty1.service` starts, agetty's login prompt would overwrite the image on tty1 the same way it always does on a normal console, undoing the whole effect. Added a second layer, `pinball-quiet-boot.yaml`, for the rest:
- `chroot $1 systemctl mask getty@tty1.service` — prevents the tty1 login prompt from ever appearing (masking, not just disabling, since `getty@tty1` is normally started via a static `getty.target.wants` symlink rather than a user-facing enable). SSH is completely unaffected.
- Appends `quiet loglevel=0 systemd.show_status=0` to `cmdline.txt` via `sed -i '$ s/$/ .../'` — pure end-of-line append, so it's safe regardless of whether `rpi-splash-screen`'s own `configure-splash` edit to the same file has already run or not (both layers' `customize-hooks:` execute in the same bdebstrap phase; their relative order isn't something we verified or need to, given the append is order-independent). Likely redundant with `fullscreen_logo`'s own text-suppression, but cheap insurance against systemd unit-status lines specifically.

Net effect: the display shows nothing but the configured image from the moment the kernel starts (initramfs) through to `multi-user.target`, and then continues showing it indefinitely afterward (nothing else is running that would paint over the framebuffer) until `mpf both <machine_folder>` starts and `mpf-mc`'s SDL2/KMSDRM backend takes the DRM master, replacing the static image with the actual game UI.

**Build succeeded and directly verified (2026-09-01)**: chroot-inspected the built image and confirmed all of: `/boot/firmware/cmdline.txt` contains `fullscreen_logo=1 fullscreen_logo_name=logo.tga vt.global_cursor_default=0 quiet loglevel=0 systemd.show_status=0`, no `console=tty1`, and the earlier PARTUUID root fix (`root=PARTUUID=50494e42-02`) intact and unaffected; `/lib/firmware/logo.tga` present at the expected placeholder file size; `/etc/systemd/system/getty@tty1.service` is a symlink to `/dev/null`; `/etc/initramfs-tools/hooks/splash-screen-hook.sh` present. **Still pending real-hardware confirmation that the image actually displays correctly** (in particular, orientation/scaling of the hand-written TGA) — chroot inspection can prove the files are correctly in place but not what actually renders on a real HDMI display.

## Public distribution: Raspberry Pi Imager custom.toml support

Goal: let people the image is distributed to configure WiFi (and hostname/user/SSH) with the same zero-friction UX every Raspberry Pi user already knows — Imager's gear-icon "OS Customisation" dialog before writing — rather than needing to SSH in and hand-edit anything.

**No fixed default account any more.** `device.user1pass`/`user1passhash` are deliberately left unset. Per `device-user-credentials.yaml`'s own documented behaviour, "if neither is set, the account will be locked" — the `pinball` UID-1000 account still exists (for group memberships, sudo, home dir) but nobody can log into it until Imager's customisation sets real credentials. This is a real behavioural change from every earlier build in this doc, and an explicit, deliberate choice for a *publicly distributed* image (shipping a fixed known default password publicly is a real exposure) — a private/personal build should set `user1pass` instead and skip all of this.

**Real architectural conflict hit and worked around: NetworkManager vs. `bookworm-minbase`'s `systemd-net-min`.** Imager's `custom.toml`/`firstrun.sh` WiFi customisation is hard-wired to NetworkManager — confirmed by reading `raspberrypi-sys-mods`'s `imager_custom` script directly: its `set_wlan()` function writes a `.nmconnection` file into `/etc/NetworkManager/system-connections/`, nothing else. Our image had no NetworkManager (bare `iwd` only). Adding rpi-image-gen's own `network-manager` layer immediately failed with:
```
Error: Provider conflict: 'network-activator' is declared by multiple layers: systemd-net-min, network-manager
```
`bookworm-minbase` hard-requires `systemd-net-min` in its own `X-Env-Layer-Requires` (not something our config can opt out of), and `network-manager`'s layer declares the exact same `Provides: network-activator` role — rpi-image-gen's dependency resolver treats this as fatal, correctly refusing to leave it ambiguous which one actually manages interfaces at runtime.

**Fix: scope NetworkManager to `wlan0` only, leave `eth0` on `systemd-networkd` untouched**, via a new custom layer (`pinball-networkmanager.yaml`) that installs `network-manager` as a **plain package**, not through rpi-image-gen's own `network-manager`/`network-manager-iwd` layers — deliberately bypassing the provider-tracking system rather than fighting it, since a hand-installed package carries no `Provides:` declaration for the resolver to conflict over:
- `/etc/NetworkManager/conf.d/iwd.conf`: `wifi.backend=iwd`, `wifi.iwd.autoconnect=false` — same iwd-backend pairing real Raspberry Pi OS Bookworm ships, so NetworkManager orchestrates connections while iwd does the actual radio work (our existing `iwd` layer is untouched, still required and still installed).
- `/etc/NetworkManager/conf.d/unmanaged-eth0.conf`: `unmanaged-devices=interface-name:eth0` — NetworkManager never touches the wired interface.
- `/etc/systemd/network/02-wlan0.network.d/10-networkmanager.conf`: `[Link]\nUnmanaged=yes` — the mirror image, telling `systemd-networkd` to leave `wlan0` alone. Found the pre-existing `01-eth0.network`/`02-wlan0.network` files by chroot-inspecting an already-built image rather than guessing; used a **drop-in directory against the existing filename**, not an edit to the file itself, specifically so it's immune to any hook-ordering race with whatever layer creates the base file (drop-ins merge with the base file at systemd parse time, at boot, not at file-write time during the build).

Net result: `eth0` and `wlan0` are fully partitioned between the two network managers, no runtime fight over either interface, and the official/tested `imager_custom` WiFi mechanism has the NetworkManager stack it expects.

**Second real gap found: installing `raspberrypi-sys-mods` alone does NOT wire up custom.toml consumption.** Read `raspberrypi-sys-mods`'s actual `firstboot` script (GitHub, `bookworm` branch) directly: it checks for `$FWLOC/custom.toml` (via `get_fw_loc`, which correctly resolves to `/boot/firmware` on this image since that's where our fstab mounts the boot partition) and calls `init_config` on it if present — but `firstboot` itself is **only ever invoked via a kernel cmdline `init=` override** (`init=/usr/lib/raspberrypi-sys-mods/firstboot`), which official Raspberry Pi OS images bake into `cmdline.txt` at their own image-creation time. Installing the package alone doesn't add that cmdline parameter — nothing calls `firstboot` without it. Added a new layer, `pinball-imager-firstboot.yaml`, appending it ourselves. Confirmed safe to always include unconditionally (not just when a user is expected to customise): if `custom.toml` doesn't exist, `firstboot` no-ops silently, still self-removes the `init=` parameter from `cmdline.txt` afterward (one-time, not sticky), and boot continues completely normally.

**Known interaction with the quiet-boot/splash work above**: when `custom.toml` *does* exist, `firstboot` runs as an early `init=` replacement — before `pinball-quiet-boot`/`rpi-splash-screen` are in effect — and shows a brief `whiptail` text dialog while applying settings, then reboots. So the very first boot after using Imager's customisation will show text for a few seconds despite the whole quiet-boot effort, then every boot after that is back to fully quiet+splashed. This is standard behaviour on real Raspberry Pi OS images too, not a regression introduced here.

**Packages added** (top-level `packages:`, plain apt installs, no custom layer needed): `raspberrypi-sys-mods`, `userconf-pi`, `ssh-import-id`, `whois`. The last two are `raspberrypi-sys-mods`/`imager_custom`'s own Recommends (SSH-key import, `mkpasswd` for password hashing) — `bookworm-minbase` builds with `Install-Recommends=off` like most mmdebstrap-based minimal images, so they need listing explicitly or `imager_custom` silently falls back to weaker file-editing paths for those features. Found this exact pattern (and the general "reuse the official Raspberry Pi Imager helpers via `userconf-pi`+`raspberrypi-sys-mods`" approach) by reading `rpi-image-gen`'s own `contrib/src/cm5-programming-jig` community example, which solves a related-but-different problem (their own custom preseed mechanism, not standard `custom.toml`) using the same underlying tools.

**Build succeeded and directly verified (2026-09-01)**: chroot-inspected the built image and confirmed: `pinball` account is UID 1000 with a locked password (`passwd -S` shows `L`); `/etc/NetworkManager/conf.d/iwd.conf` and `unmanaged-eth0.conf` present with correct content; `/etc/systemd/network/02-wlan0.network.d/10-networkmanager.conf` present; `NetworkManager.service`/`NetworkManager-wait-online.service` enabled; all five new packages installed (`network-manager`, `raspberrypi-sys-mods`, `userconf-pi`, `ssh-import-id`, `whois`); `/usr/lib/userconf-pi/userconf` and `/usr/lib/raspberrypi-sys-mods/imager_custom` present; final `cmdline.txt` correctly composes all four independent features added across this session (PARTUUID root fix, splash screen, quiet boot, and this `init=firstboot` trigger) with no conflicts between any of them. **Still pending real-hardware verification of the actual end-to-end flow** — flash via Raspberry Pi Imager with the gear-icon WiFi/hostname/user fields filled in, confirm first boot applies them and connects to WiFi, confirm subsequent boots are normal. Nothing about this can be proven via chroot inspection alone.

**Removed**: the build-time-baked WiFi profile (`iwd.profile:` pointing at gitignored `pinball/wifi/Space.psk`) is gone from `pinball.yaml`. Two independent reasons, not just "superseded by custom.toml": (1) baking a personal home network's real credentials into a binary `.img` that gets distributed to other people would leak them regardless of gitignore, since gitignore only protects the *source repo*, not the built artifact; (2) it would have silently stopped working anyway once NetworkManager owns `wlan0` — NetworkManager manages connections through its own `.nmconnection` profiles via D-Bus, not iwd's native `/var/lib/iwd/*.psk` files, once it's the one driving the interface. `pinball/wifi/Space.psk` itself is now unused and can be deleted whenever convenient (still gitignored either way, so leaving it costs nothing but real personal WiFi credentials sitting in a local file with no remaining purpose).

### Getting the Customisation step to actually appear in Raspberry Pi Imager

Everything above makes the *image* capable of consuming Imager's customisation data. It doesn't make Imager *offer* that step in the first place for a raw, unrecognized `.img` file -- confirmed by hitting this directly: picking our `.img` via Imager's "Use custom" file picker skips the Customisation step entirely, every time, regardless of what the image itself supports.

**Root cause**: Imager has no way to know what a random local file supports. It only shows the Customisation step for OS-list entries carrying real metadata (`init_format`, `devices`, checksums, etc). "Use custom" is a raw file picker with none of that attached, by design -- not a bug, and not something fixable from inside the image itself.

**Imager 2.0 (November 2025) also changed the mechanism this hinges on**: the old gear-icon/Ctrl+Shift+X customisation dialog is gone; customisation is now its own wizard step, and `init_format` gained a new value, `cloudinit-rpi`, which the *current* official Raspberry Pi OS images use (a real `cloud-init` NoCloud-datasource implementation, not the classic `raspberrypi-sys-mods`/`custom.toml` flow this project already has installed and verified). The older value, `"systemd"`, is still supported and is exactly what our image supports (`raspberrypi-sys-mods`'s `firstboot`, `custom.toml`, `userconf-pi`, scoped NetworkManager, all built and chroot-verified above) — full `cloudinit-rpi` support (real `cloud-init` + Netplan + a NoCloud seed on the boot partition) is a materially bigger, separate lift we have not done.

**Fix: give Imager an explicit local manifest describing our image**, rather than using "Use custom". Raspberry Pi's own `os_list`/manifest JSON schema (`raspberrypi/rpi-imager` repo, `doc/json-schema/os-list-schema.json`) requires `name`, `description`, `icon`, `url`, `extract_size`, `extract_sha256`, `image_download_size`, `release_date`, `devices` per entry, plus the optional `init_format` field. `extract_sha256` in particular is strictly enforced -- Imager aborts the flash if it doesn't match, so this can't be hand-typed once and forgotten; it has to be regenerated per build.

The official `create_local_json.py` helper (also in `raspberrypi/rpi-imager`, `doc/local_json/`) does **not** cover this case -- it only re-attaches metadata to local copies of *already-known* official images (matched against the online catalog by name/checksum), and silently skips anything it can't match. For a genuinely custom third-party image there's no official generator; the manifest has to be authored directly.

Wrote `imager-repo.sh` (repo root) to do this: finds the newest `.img` in `pinball/deploy/` (or takes one as an argument), computes its real size/sha256, and writes `pinball/deploy/local_repo.json` (gitignored, like everything else in that directory) with `"init_format": "systemd"` and `"devices": ["pi5"]`. Point Imager at it via **App Options → Content Repository → EDIT → Use custom file → select the file → APPLY & RESTART** (confirmed exact menu path from Imager's own documentation) -- Imager then shows a new OS-list entry ("Pinball Machine (dev build)") to select instead of "Use custom", and *that* entry should surface the Customisation step. Note Imager forgets a custom content repository selection on restart (a deliberate security choice, not a bug) -- it has to be re-selected each session.

**First real-world test found another gap, root-caused via Imager's own source (not docs, which don't cover this)**: with the custom repository active and "Raspberry Pi 5" selected as the device, the OS list came up completely empty (just the built-in "Erase"/"Use custom" entries) -- not even our own manifest entry showed up. Read `imagewriter.cpp` directly (`raspberrypi/rpi-imager`, `qml` branch) to find out why: the device-tag filter used to decide whether an `os_list` entry's `"devices"` array matches the currently-selected hardware (`hw_filter`, built in `createHardwareTags()`) is populated **entirely from the active repository's own top-level `imager.devices` array** -- `imager.toObject().value("devices")` -- with no fallback to Imager's built-in device catalog. Our manifest omitted that block entirely, so `hw_filter` was empty, and `filterOsListWithHWTags()` silently drops any entry that declares a `"devices"` array when none of its tags are in (empty) `hw_filter` -- which is exactly what happened to our own entry. The "Choose Device" step still worked normally because it draws from Imager's own bundled default catalog, a separate code path from this filter -- so there was no visible error, just an empty list once you'd actually picked a device.

**Fix**: `imager-repo.sh` now also emits a top-level `"imager": {"devices": [...]}` block, with a `"Raspberry Pi 5"` entry declaring `"tags": ["pi5"]` (matching the schema's own Pi 4 example: `name`/`description`/`tags`/`matching_type`, `matching_type` defaulting to `exclusive`) -- giving `hw_filter` something to actually match our own `os_list` entry's `"devices": ["pi5"]` against.

**Second real-hardware test, entry now visible and selectable -- found a real, serious boot failure.** With the `imager.devices` fix above, "Pinball Machine (dev build)" showed up and could be selected/customised. Flashing it and booting: boot 1 applies the SSH/customisation correctly (confirmed -- SSH config visibly applied), then reboots as expected -- but boot 2 fails hard: screen goes black, PWR LED solid red (power confirmed fine, official 27W supply), no SSH, and it never reboots again, just sits there. Even with `pinball-quiet-boot`/`rpi-splash-screen` disabled for debug visibility (see below), it happened too fast to read on screen.

**Diagnosis required pulling the SD card and reading it offline** -- imaged the whole card with `dd` (from the user's Mac, since the sandboxed environment can't supply an interactive `sudo` password) and mounted it through the same Docker container used for every other image inspection in this doc. First finding: the MBR disk identifier had changed from our build-time `0x50494e42` to a fresh random `0x460ab223` -- traced to `raspberrypi-sys-mods`'s `firstboot` script (read directly from GitHub, `bookworm` branch) unconditionally calling a `fix_partuuid()` function whenever the boot partition is partition 1 (true for our `mbr/simple_dual` layout), which rewrites the MBR disk signature via `fdisk`'s expert-mode disk-identifier command using a fresh hardware-RNG value -- a deliberate official-Raspberry-Pi-OS anti-collision measure (every card gets a unique signature on first boot, since many cards get flashed from the same source image). **This part turned out to be a red herring**: `fix_partuuid()` also correctly self-corrects `/etc/fstab` and `cmdline.txt` via `sed`, replacing the old disk ID with the new one -- verified directly on the crashed card that both files correctly read `PARTUUID=460ab223-02`, matching the actual (new) MBR signature. Our `image.disksig` + `pinball/pre-image.sh` PARTUUID-pinning approach survives this self-rewrite intact and did not cause the crash.

**The actual cause, found in the same `cmdline.txt`**: alongside the correctly-updated `root=PARTUUID=460ab223-02`, it still contained `systemd.run=/boot/firstrun.sh systemd.run_success_action=reboot systemd.unit=kernel-command-line.target` -- Raspberry Pi Imager's *own*, separate customisation-injection mechanism (written because our manifest declared `init_format: "systemd"`), completely independent of the `raspberrypi-sys-mods`/`custom.toml` pipeline this project built and wired up via `pinball-imager-firstboot.yaml`'s own `init=/usr/lib/raspberrypi-sys-mods/firstboot` cmdline addition. Both mechanisms exist to do the same job (apply Imager's customisation data on first boot), and having both active collided:

- Boot 1: our `init=/usr/lib/raspberrypi-sys-mods/firstboot` is a kernel-level `init=` override -- it replaces PID 1 entirely for that boot, so `systemd` (and therefore anything keyed off `systemd.run=`/`systemd.unit=` kernel parameters) never starts at all. Our own mechanism runs to completion (applies SSH config, confirmed working), then self-removes its own `init=` parameter from `cmdline.txt` (its own documented, verified-safe behaviour) and reboots. Imager's `systemd.run=/boot/firstrun.sh` parameter is untouched by any of this -- it was simply never reached.
- Boot 2: our `init=` parameter is gone now, so the kernel boots normally into `systemd` for the first time -- which immediately honours the still-present `systemd.unit=kernel-command-line.target`. This is a special systemd target that runs *only* the unit generated from `systemd.run=`, deliberately skipping the normal `multi-user.target` graph entirely (no display manager, no network bring-up, no getty). `firstrun.sh` (Imager's generated script) then hangs or fails partway -- plausibly because `raspberrypi-sys-mods`'s own mechanism already did the same renaming/network-config work on boot 1, so re-running the same `userconf`/`nmcli` commands against already-changed state doesn't hit the preconditions Imager's script assumes. Either way, since `kernel-command-line.target` never proceeds to a normal boot, the result is exactly what was observed: black screen, no SSH, no further reboots -- the system is technically running, just parked in a target with nothing user-visible attached.

**Fix**: removed `pinball-imager-firstboot.yaml` from `pinball.yaml`'s `layer:` list entirely (kept the file, commented out the reference, for the same reason other superseded pieces in this doc are kept rather than deleted). Imager's own `init_format: "systemd"` mechanism is a complete, self-contained, self-cleaning trigger on its own -- it doesn't need our manual `init=` wiring, and having both was the actual bug, not a missing piece. `raspberrypi-sys-mods`, `userconf-pi`, `ssh-import-id`, `whois`, and the scoped `network-manager` setup all stay exactly as built -- `firstrun.sh` calls the same underlying tools (`userconf`, `nmcli`, `raspi-config`), it just needed to be the *only* trigger, not one of two.

**Lesson**: this is the same class of blind spot as every other bug in this doc -- invisible to chroot inspection, only surfaces on real hardware, and specifically only on the *second* boot in this case (the first boot looked completely successful). Don't trust "it applied the customisation fine" as proof the whole flow works; the interesting failure was one boot later.

**Not yet re-verified** -- rebuild in progress as of this writing. `pinball-quiet-boot`/`rpi-splash-screen` are still deliberately disabled (commented out, see the `layer:` list) pending a clean two-boot cycle; re-enable both once confirmed.

### Third real-hardware test: Imager's OWN mechanism turned out to be broken too

With `pinball-imager-firstboot` removed (per the fix above), the SAME symptom recurred: boot 1 applies nothing, boot 2 screen black, LED solid red, no SSH, no further reboots. Pulled the SD card again (same `dd` + Docker-mount process) and this time read the *contents*, not just cmdline.txt:

- `cmdline.txt` still had `systemd.run=/boot/firstrun.sh systemd.run_success_action=reboot systemd.unit=kernel-command-line.target` -- meaning `firstrun.sh` (Imager's own generated script, confirmed present, unmodified, still sitting on the boot partition) never reached ITS OWN final cleanup line either.
- Checked exactly which of `firstrun.sh`'s steps actually applied by reading `/etc/hostname`, `/etc/shadow`, `~/.ssh/authorized_keys`, and `/etc/NetworkManager/system-connections/`: **none of them did.** Hostname unchanged, account still locked, no SSH key, no WiFi profile.

Conclusion: this isn't a conflict between two mechanisms -- Imager's own `systemd.run=/boot/firstrun.sh` mechanism hangs on this image even running completely alone, on its very first real command (`imager_custom set_hostname ...` → `raspi-config nonint do_hostname`). Read `raspi-config`'s `do_hostname` source directly; its own D-Bus-dependent path is correctly guarded (`systemctl -q is-active dbus` before calling `hostnamectl`), so the exact hang point wasn't pinned down further -- not worth chasing deeper into `raspi-config`'s internals when a working alternative already existed.

**Fix**: re-enabled `pinball-imager-firstboot` (our own `custom.toml`/`raspberrypi-sys-mods` pipeline, which DID apply SSH correctly in the very first real-hardware test) and extended it to neutralise Imager's redundant, broken trigger -- patching the *installed* `/usr/lib/raspberrypi-sys-mods/firstboot` script in place so that, at the exact point it already cleans its own `init=` parameter out of `cmdline.txt` (right before calling `main()` and rebooting), it ALSO strips `systemd.run=`/`systemd.run_success_action=`/`systemd.unit=kernel-command-line.target`. That guarantees the cleanup runs before any reboot regardless of what `main()` does, and means Imager's broken mechanism never gets a chance to run at all.

### Getting that patch to actually build: three real bugs, in order

**Bug 1 -- wrong install phase.** First attempt embedded the patch script as a `cat <<'EOPY' > ...` heredoc directly in the customize-hook and declared `raspberrypi-sys-mods` in top-level `packages:` (matching how it was originally added). Build failed immediately: `FileNotFoundError: .../firstboot`. Root cause: top-level `packages:` entries are installed by a separate, later-numbered bdebstrap hook that runs **after** every layer's own `customize-hooks:`, not before -- confirmed by finding that stage's install command explicitly listed in the `bdebstrap` invocation's `--env IGconf_packages_N=...` args, separate from the `--config <layer>.yaml` merges that drive the shared early "essential" package-install phase. Fix: moved `raspberrypi-sys-mods` into `pinball-imager-firstboot.yaml`'s own `mmdebstrap: packages:` list, guaranteeing it installs during the same early phase as every other layer's packages, before any customize-hooks run.

**Bug 2 -- heredoc corruption.** With the file present, the build still failed, now on our own `sys.exit("anchor line not found")` check inside the python patch script. Isolated it by testing the *exact* python logic standalone against a real extracted copy of the installed `firstboot` file (pulled from an earlier successful build) -- it worked perfectly outside the YAML pipeline. The difference: the heredoc-embedded version, once run for real inside `bdebstrap`'s own hook execution, apparently doesn't survive intact -- almost certainly the same class of bug hit earlier in this project's `Dockerfile` (an apostrophe inside a single-quoted `bash -c '...'` block prematurely closing the string): our python source legitimately needs literal single-quote characters to represent the sed syntax it's matching (`'s| init=...||'`), and those don't survive nested inside however `bdebstrap` itself wraps the whole hook body. Fix: stopped embedding the script as a heredoc entirely -- wrote it as a real file (`pinball/layer/pinball-patch-firstboot.py`), installed via `install -m 755 <src> $1/tmp/...` and run via `chroot $1 python3 /tmp/...`, so its content never has to survive a trip through any shell's quoting at all.

**Bug 3 -- the verification check itself, not the patch.** Even after fixing both of the above, the SAME "expected patch not found" failure persisted, now genuinely confusing since the exact same script had just been proven correct against real file content. Added temporary diagnostics (copying the installed file to the bind-mounted `pinball/deploy/` directory before and after the patch step, plus explicit exit-code/md5 echoes) to get real evidence instead of re-guessing -- `install` succeeded with matching checksums, `python3` exited 0, and the "after" snapshot, inspected directly on the host, clearly showed the correct line inserted in the correct place. The bug was in the *verification grep* itself: `grep -q systemd.unit=kernel-command-line` assumes exactly one character between "systemd" and "unit", but the inserted text (correctly) contains `systemd\.unit=kernel-command-line` -- a literal backslash *and* dot (the backslash needed to escape the dot for sed's own regex), two characters, which a bare unescaped `.` in the checking grep's pattern can't span. The patch had been applying correctly since the very first attempt with the robust substring-based Python matcher (bug 2's fix) -- this was purely a check bug, chased across three rebuild cycles before being found by direct evidence rather than more pattern-reasoning. Fixed by switching to `grep -qF 'kernel-command-line'` (fixed-string mode, no regex ambiguity at all, matching a substring that only ever appears in our own inserted text).

**Lesson, again**: when a check keeps failing despite the thing it's checking being independently verified correct, suspect the check before re-deriving the fix from scratch. Pulling real before/after file snapshots onto the host (via a temporary debug hook copying into the bind-mounted `deploy/` dir) settled this in one build cycle, after three cycles of re-theorizing without that evidence.

**Build succeeded and directly verified (2026-09-03)**: `pinball-09-03-2026-2013.img` -- chroot-confirmed `cmdline.txt` contains `init=/usr/lib/raspberrypi-sys-mods/firstboot` and the patched `firstboot` script has the `systemd.run=`/`systemd.unit=kernel-command-line.target` stripping line correctly inserted right after its own `init=` self-removal line. `imager-repo.sh` re-run for this image.

### Fourth real-hardware test: fixed the crash, but broke the actual customisation

Flashed and tested `pinball-09-03-2026-2013.img`. Boot no longer crashes -- clean success on that front. But the customisation genuinely wasn't applied at all: reached the login prompt, account still locked, couldn't log in. Last console lines before the prompt: `Reached target multi-user.target`, `Finished systemd-update-utmp-runlevel.service` -- a completely normal, un-hung boot completion.

This pins down exactly what the previous fix actually did: **Raspberry Pi Imager's `init_format: "systemd"` only ever writes `/boot/firstrun.sh` to the boot partition -- confirmed directly by reading it, no `custom.toml` is written for this format at all.** That means:
- Our own `custom.toml`/`raspberrypi-sys-mods` pipeline (`pinball-imager-firstboot`) never had any data to apply in the first place, on any of the real-hardware tests in this saga. It wasn't broken -- it was reading a file Imager never writes for this init_format.
- `firstrun.sh` (regenerated fresh by Imager at every flash, with the user's actual choices baked directly into its literal shell commands) is the *only* thing that ever carries real customisation data for this init_format.
- The "fix" that resolved the crash -- patching `firstboot` to strip `systemd.run=`/`systemd.unit=kernel-command-line.target` from `cmdline.txt` -- didn't just prevent the hang, it prevented `firstrun.sh` from ever being invoked at all. No crash, but also nothing applied: exactly what this test showed.

**Re-disabled `pinball-imager-firstboot` again** (commented out in `pinball.yaml`, file kept for reference like everything else in this saga) -- both its `init=` trigger and its `systemd.run=` stripping. `firstrun.sh` is once again the sole, un-tampered-with customisation trigger. This puts the actual, still-unsolved problem back in view: `firstrun.sh` hangs on its first real command (traced earlier to `imager_custom set_hostname` → `raspi-config nonint do_hostname`, exact blocking point not pinned down from source reading alone).

**Added `pinball-debug-shell.yaml`** instead of continuing to guess from upstream source: a single-line layer appending `systemd.debug-shell=1` to `cmdline.txt`, giving a passwordless root shell on tty9 (Ctrl+Alt+F9 on the physical console) at any point during boot, hang or not. This is a real, unauthenticated-root-shell security exposure and is explicitly a temporary debugging aid -- remove before any distribution, once `firstrun.sh`'s actual hang is root-caused and fixed at its source (patching whatever raspi-config/imager_custom call is actually blocking, the same way `pinball-bootdev-fix` patches `rpi-bootdev-tag` -- a real, static, build-time-patchable file, unlike the dynamically-generated `firstrun.sh` itself).

**Build succeeded and directly verified (2026-09-03)**: `pinball-09-03-2026-2037.img` -- chroot-confirmed `cmdline.txt` is back to a clean baseline plus the debug aid: `console=serial0,115200 console=tty1 root=PARTUUID=50494e42-02 fsck.repair=yes rootwait systemd.debug-shell=1` -- no `init=`, no stripped `systemd.run=`. `imager-repo.sh` re-run.

### Fifth real-hardware test: same hang, live debug shell not confirmed usable

Flashed and tested `pinball-09-03-2026-2037.img`. Same symptom as the very first crash in this saga: screen black, PWR LED (solid, not blinking -- already ruled out as a power issue), no response. Asked whether Ctrl+Alt+F9 (the `systemd.debug-shell=1` tty9 shell) produced any visible change at all -- never got a clear answer either way before the conversation moved straight to pulling the card again, so live-shell access was never actually confirmed working or not working. Not pursued further -- pulling the card had already produced hard evidence multiple times this saga, faster than continuing to troubleshoot an unconfirmed live-access path.

Pulled the card a third time (same `dd` + Docker-mount process). Confirmed, yet again: `firstrun.sh` still present and unrun, `cmdline.txt`'s `systemd.run=`/`systemd.unit=kernel-command-line.target` untouched (as expected, since the stripping patch is disabled), hostname/password/SSH/WiFi all still unapplied. Fully reproducible, same point every time: the very first thing `firstrun.sh` does (`imager_custom set_hostname` → `raspi-config nonint do_hostname`).

**Fix: patch the exact call, not the whole mechanism.** Added `pinball-patch-imager-custom.yaml` (+ `pinball-patch-imager-custom.py`, following the same file-based-patch pattern established for `pinball-imager-firstboot` after the heredoc-corruption bug above -- no reason to risk that class of bug again) removing just the `raspi-config nonint do_hostname "$HOSTNAME"` line from the installed `/usr/lib/raspberrypi-sys-mods/imager_custom`'s `set_hostname` function. The function's own direct `echo "$HOSTNAME" > /etc/hostname` line (right after it) is untouched, so hostnames still apply -- just without whatever `raspi-config` itself blocks on. Deliberately narrow: only this one line in this one function. `imager_custom`'s other functions (`enable_ssh`, `set_wlan`, `set_keymap`, `set_timezone`) are left completely alone -- no evidence any of those hang too, and `set_wlan` specifically is the thing writing a correct NetworkManager `.nmconnection` profile; falling all the way back to `firstrun.sh`'s own `wpa_supplicant.conf`-writing else-branch (which only activates if `imager_custom` is entirely *absent* -- not exercised by this fix) would not even be picked up by our NetworkManager-based network stack.

Known tradeoff, accepted rather than fixed: `raspi-config`'s `do_hostname` also updates `/etc/hosts`' `127.0.1.1` line to match; skipping the call means that line goes stale (keeps showing the placeholder hostname) after a real hostname change. Cosmetic -- doesn't block SSH, WiFi, or the password change, which all still need to be verified as the next real-hardware test.

Verified the patch script directly against a real extracted `imager_custom` (pulled from an earlier successful build, same verification discipline established after the earlier heredoc/verification-check bugs) before trusting it in a full build: confirmed the `do_hostname` line is gone and the function's remaining body is intact.

**Build succeeded and directly verified (2026-09-03)**: `pinball-09-03-2026-2114.img` -- chroot-confirmed `/usr/lib/raspberrypi-sys-mods/imager_custom` no longer contains `raspi-config nonint do_hostname`, and `set_hostname`'s remaining body (`echo "$HOSTNAME" > /etc/hostname`) is intact. `imager-repo.sh` re-run. **Not yet verified on real hardware** -- this is a hypothesis (the most-eliminated candidate from five rounds of testing) narrowed down as precisely as static analysis and reproducible SD-card evidence allow, but `raspi-config`'s broader startup logic (before it even reaches `do_hostname`'s own body) was never ruled out as an alternate blocking point, since no live process state was ever actually captured. If this doesn't resolve it, the next step is to get real live evidence -- either by confirming `systemd.debug-shell` actually renders on this hardware, or via a serial console -- rather than continuing to eliminate candidates by inspection alone.

### Sixth real-hardware test: same crash. Architectural pivot away from `init_format: "systemd"` entirely

The `imager_custom` patch didn't fix it either -- same symptom, same as the very first crash: screen black, PWR LED solid (power confirmed fine, again), no response. Five real-hardware test cycles (custom.toml via our own `init=` trigger; neutralising Imager's `systemd.run=` trigger; reverting that and adding a debug-shell; patching `imager_custom`'s `do_hostname` call specifically) had all been narrowing down *which line* inside Imager's `systemd.run=/boot/firstrun.sh` → `kernel-command-line.target` mechanism was responsible, without ever getting live process state to confirm any of it (`systemd.debug-shell`'s tty9 access was never confirmed to actually render on this hardware). At this point the user pushed back -- rightly -- that continuing to patch deeper into the same black-box mechanism, one slow rebuild-flash-test cycle at a time, wasn't converging.

**Stepped back and questioned the premise instead of the next patch target.** The actual requirement was never "make `systemd.run=`/`kernel-command-line.target` work" -- that was just the mechanism `init_format: "systemd"` happens to use. Re-read Raspberry Pi Imager's own `os_customisation_formats.md` for what the *other* init_format values actually do, and found `"rpi-preseed"`: Imager writes a single plain `/boot/firmware/rpi-preseed.toml` file, with **no `cmdline.txt` modification at all** -- no `init=`, no `systemd.run=`, no special early-boot target. Consumption is "gated on the presence of the file" -- i.e. a normal systemd `ConditionPathExists=`, evaluated during ordinary `multi-user.target` boot. This sidesteps every mechanism responsible for every hang/crash in this entire saga, not just the one we'd most recently patched.

Confirmed the TOML schema before committing to it (found a community example gist showing the full field set: `config_version`, `[system].hostname`, `[user].name/password/password_encrypted`, `[ssh].enabled/password_authentication/ssh_import_id/authorized_keys`, `[wlan].ssid/password/password_encrypted/hidden/country`, `[locale].keymap/timezone`) -- and cross-checked it against this project's own real `firstrun.sh` capture from earlier in this saga, which uses the identical field shapes via `imager_custom` calls. Notably confirmed from that real capture that Imager's WiFi `password` field is a **pre-derived 64-hex-character WPA-PSK**, not a plaintext passphrase (`imager_custom set_wlan 'Space' 'bc404e13a030630811a6f3af98b5e80e22dd0fc0f8a3c80d35a02e8021be1f51' 'US'`) -- both `wpa_supplicant` and NetworkManager's keyfile format accept a raw hex PSK directly in their `psk=` field, so it can be passed straight through with no re-encoding.

**Wrote our own minimal consumer from scratch** (`pinball-preseed.yaml` + `pinball-apply-preseed.py`) rather than reusing `raspberrypi-sys-mods`/`imager_custom`/`raspi-config` -- those are exactly the components five rounds of real-hardware testing traced every hang in this saga to, so there was no reason to route through them again just because the trigger mechanism changed. Uses only tools already independently proven working on this image:
- **User rename+password**: `/usr/lib/userconf-pi/userconf <name> <hash>` -- the same UID-1000-based renamer already confirmed correct earlier in this project, called directly, bypassing `imager_custom`/`raspi-config` entirely.
- **WiFi**: writes a NetworkManager `.nmconnection` file directly into `/etc/NetworkManager/system-connections/` -- matches exactly what `pinball-networkmanager`'s scoped NetworkManager setup already expects, and avoids depending on `nmcli`/D-Bus being available at the point this runs.
- **Hostname/SSH keys/locale**: plain file writes (`/etc/hostname`, `/etc/hosts`, `~/.ssh/authorized_keys`, `/etc/timezone`, `/etc/default/keyboard`) -- the same patterns `firstrun.sh`'s own `imager_custom`-absent fallback branches already use (which we'd read in full during earlier debugging), just without the parts of that chain that hang.
- **Password hashing**: Python's stdlib `crypt.crypt(pw, crypt.mksalt(crypt.METHOD_SHA512))`, matching `raspberrypi-sys-mods`'s own `init_config` hashing scheme (confirmed by reading its source earlier in this project) -- no `whois`/`mkpasswd` dependency needed. Confirmed Python 3.11 (Bookworm's default, includes the stdlib `tomllib` TOML parser needed here) is what's actually installed on this image, not assumed.

**Verified before building, not after**: syntax-checked the script (`py_compile`); parsed a realistic sample TOML (built from this project's own real `firstrun.sh` capture -- same hostname/user-hash/SSH-key/WiFi-PSID/timezone values) through `tomllib` inside the actual build container (confirmed `tomllib` import succeeds on the real target Python); ran the WiFi `.nmconnection`-generation and password-hashing logic in isolation against that sample data and checked the output by hand (well-formed keyfile syntax; hash round-trips correctly via `crypt.crypt(pw, hash) == hash`). This is the same discipline adopted after the heredoc-corruption and verification-check bugs earlier in this saga: don't trust logic in a ~60-minute build cycle without testing it directly first.

### Seventh real-hardware test: no crash, hostname/user/SSH all correct -- but a genuinely new discovery about how Imager actually works

Flashed and tested `pinball-09-03-2026-2204.img`. **The boot itself is finally fully fixed**: no crash, reached a normal login prompt, logged in with the exact username/password set in Imager's dialog, hostname correct. This closes out the entire boot-hang saga from the six real-hardware tests above -- the `rpi-preseed` pivot away from `systemd.run=`/`kernel-command-line.target` worked.

WiFi didn't come up, though. With login access finally available, diagnosis moved to live SSH commands instead of SD-card pulls -- much faster iteration. `journalctl -u pinball-preseed` showed **"No entries"** -- our own service never ran at all. `systemctl status pinball-preseed` confirmed why: `ConditionPathExists=/boot/firmware/rpi-preseed.toml was not met` -- Imager never wrote that file. Checking the filesystem directly revealed the real mechanism: **Imager applies most customisation fields by directly editing the target partitions on the host machine immediately after flashing** -- not through any boot-time file at all, regardless of the declared `init_format`. `/etc/hostname`, the renamed/repassworded user account, and SSH access all came from this direct-write step. `cmdline.txt` also picked up `cfg80211.ieee80211_regdom=US`, another sign of the same direct-edit behaviour, appended independent of anything we configured.

WiFi got the same direct-write treatment: a real `/etc/NetworkManager/system-connections/Space.nmconnection` was present, written straight onto the disk at flash time, well-formed, valid UUID, correct SSID -- yet `wlan0` sat `disconnected` and NetworkManager's own log never showed it even attempting activation of that profile (contrast with `lo`, which explicitly logs "Activation: starting connection 'lo'" -- `Space` never got an equivalent line). Manually running `nmcli connection up Space` reproduced it interactively: `Error: Connection activation failed: Secrets were required, but not provided`, despite `nmcli -s connection show Space` proving NetworkManager's own connection store had the exact right PSK loaded (`psk-flags: 0`, full value present). The stored secret was correct and NetworkManager had it -- yet activation behaved as if it didn't.

**Root cause, confirmed by direct A/B test on real hardware**: the PSK in that file is a **pre-derived 64-hex-character WPA-PSK** (`bc404e13a030630811a6f3af98b5e80e22dd0fc0f8a3c80d35a02e8021be1f51`), not the plaintext WiFi passphrase -- Imager deliberately never writes the plaintext password anywhere, converting it to the PSK form immediately (standard, sensible security practice on Imager's part). Tested directly: `sudo nmcli device wifi connect Space password <the real plaintext passphrase>` connected immediately, on the same hardware, same SSID, same everything except using a plaintext passphrase instead of the stored raw-hex PSK. This isolates the bug precisely to **NetworkManager's `iwd` backend not correctly handing a raw hex PSK to iwd's own secret-agent protocol**, even though NetworkManager's own connection store holds it correctly -- a real integration gap between NetworkManager 1.42.4 and `iwd`, not anything wrong with our config, Imager's output, or the network itself.

**Fix**: switched `pinball-networkmanager`'s wifi backend from `iwd` to NetworkManager's own default (`wpa_supplicant`-based) -- the far more common, thoroughly-tested combination, and one with no known issue handling raw hex PSKs (this is completely standard `wpa_supplicant.conf` `psk=<64-hex>` syntax, which `wpa_supplicant` has supported natively for decades). Since Imager's PSK format isn't something this project controls, the fix had to be on the consuming side. Removed the `iwd` layer from `pinball.yaml` entirely (previously `wifi: iwd`) rather than leaving it installed-but-unused -- running both `iwd` and `wpa_supplicant` against the same `wlan0` radio would reintroduce the exact class of dueling-daemon conflict `pinball-networkmanager`'s eth0/wlan0 scoping was built to avoid in the first place. Added `wpasupplicant` as an explicit package on `pinball-networkmanager` (NetworkManager's own dependency on it may only be a Recommends, and this project's base already builds with `Install-Recommends=off`).

**Build succeeded and directly verified (2026-09-04)**: `pinball-09-04-2026-2251.img` -- chroot-confirmed `wpasupplicant` installed, `iwd` package entirely absent, and `/etc/NetworkManager/conf.d/` contains only `unmanaged-eth0.conf` (no more `iwd.conf`). `imager-repo.sh` re-run.

**CONFIRMED on real Pi 5 hardware (2026-09-08): WiFi connects successfully.** This closes out the entire Raspberry Pi Imager customisation saga -- seven real-hardware test cycles across boot crashes (`systemd`/`kernel-command-line.target` hangs), the architectural pivot to `rpi-preseed`, and finally this WiFi-specific NetworkManager+`iwd` PSK bug. End state: hostname, user account/password, SSH, and WiFi are all confirmed working from a single Imager OS-Customisation flash, using `init_format: "rpi-preseed"` (even though Imager, in practice, applies most of this directly to the disk at flash time rather than through the `rpi-preseed.toml` mechanism itself -- `pinball-preseed`/`pinball-apply-preseed.py` remain in place as a correct, tested fallback for whatever Imager *does* defer to boot time, but the direct-write behaviour is what's actually been exercised and confirmed in these tests).

Should be removed before shipping to anyone else.
